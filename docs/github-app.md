# GitHub App and GitHub access

Omakaze reads pull requests, diffs and file contents from GitHub and posts comments and reviews back. A workspace gets access to repositories through one or more **connections**:

| Connection | Set up by | Best for |
| --- | --- | --- |
| GitHub App installation | A workspace admin, from **Settings → GitHub → Install on GitHub** | Organizations: choose repositories on GitHub, receive webhooks, post summary comments as the app |
| Personal access token | A workspace admin, from **Settings → GitHub → Connect with a token** | A bot account, or instances without a GitHub App |
| Linked GitHub account | A workspace admin, from **Settings → GitHub → Use your GitHub account** | Personal workspaces |

The GitHub App is also what enables **Sign in with GitHub** unless you configure an OAuth App instead (see [Sign in with GitHub](#sign-in-with-github)).

## Create the app from /admin

An instance admin can create the GitHub App in one step with GitHub's app manifest flow.

1. Set `APP_URL` to the URL of the instance and restart it. The app's URLs are derived from it.
2. Open `/admin`.
3. Choose **Create GitHub App on my account**, or enter an organization login and choose **Create for organization** to create an app owned by that organization.
4. GitHub shows the app settings filled in. Confirm the creation; you can change the name first if it is already taken.
5. GitHub redirects back to `<APP_URL>/api/github/manifest`. Omakaze exchanges the one-time code for the app's ID, slug, private key, webhook secret, client ID and client secret, and stores them encrypted in the database. `/admin` then shows the app.

The request must be completed within an hour by the same admin who started it. **Remove stored app** on `/admin` deletes the stored credentials; it does not delete the app on GitHub.

### What the manifest creates

The settings come from `buildAppManifest` in `src/lib/github/app.ts`:

| Setting | Value |
| --- | --- |
| Name | `Omakaze (<host of APP_URL>)` |
| Homepage URL | `<APP_URL>` |
| Callback URL (user sign-in) | `<APP_URL>/api/auth/github/callback` |
| Setup URL | `<APP_URL>/api/github/setup`, also called after an installation is updated |
| Webhook | Active, sent to `<APP_URL>/api/github/webhook` with a secret generated by GitHub. Left out when `APP_URL` is localhost or a private address, which GitHub rejects |
| Request user authorization during installation | Off |
| Visibility | Private (`public: false`) |
| Repository permissions | Contents: read, Metadata: read, Pull requests: read and write, Issues: read and write, Checks: read and write, Commit statuses: read and write |
| Account permissions | None. GitHub rejects Email addresses in a manifest; add it afterwards (below) |
| Events | Pull request, Pull request review, Pull request review comment, Pull request review thread (only with a webhook) |

What the permissions are used for:

| Permission | Used for |
| --- | --- |
| Contents: read | File contents at the pull request head and merge base (context expansion, the `read_file` tool), and the comparison that finds the merge base |
| Metadata: read | Repository information; GitHub requires it for every app |
| Pull requests: read and write | Pull requests, changed files, review comments, replies and reviews, and resolving review threads (GraphQL) |
| Issues: read and write | The summary comment in the pull request conversation (`issues/<number>/comments`) |
| Checks: read and write | The [guide check](#guide-check) as a check run named "Omakaze guide", for app installations |
| Commit statuses: read and write | The guide check as a commit status, for [linked-account connections](#linked-github-account) whose credential is a user token of this app (GitHub limits those tokens to the app's permissions) |
| Email addresses: read | The verified email addresses of users who sign in with GitHub: the address of a new account, confirmation for email-restricted invites, and `AUTH_ALLOWED_EMAIL_DOMAINS` |

GitHub doesn't accept the email permission in a manifest, so add it after creating the app: open the app's **Permissions & events** page (linked from `/admin`), set **Account permissions → Email addresses** to **Read-only** and save. Without it, only the public email of a user's GitHub profile is used. `/admin` points this out with a link to the app's permission settings on GitHub, where it can be added.

Omakaze acts on the `pull_request`, `pull_request_review`, `pull_request_review_comment` and `pull_request_review_thread` events, and on `installation` events, which GitHub sends to every app. Other deliveries are recorded as ignored. See [Webhooks](#webhooks).

### Apps created before an event was added

GitHub keeps an app's event subscriptions as they were when it was created, so an app created before `pull_request_review_thread` was added to the manifest does not receive it. Conversations resolved on GitHub then appear in Omakaze when it next reads the review threads (it keeps them for 10 seconds; open pages refresh every 30 seconds) instead of right away.

`/admin` compares the app's subscriptions with the manifest (`APP_EVENTS` in `src/lib/github/app.ts`) through `GET /app`, and lists missing events in the GitHub App panel with a link to the app's **Permissions & events** page. The check runs for apps created on `/admin` and for apps configured with environment variables. To subscribe:

1. Open the app's settings on GitHub (the link on `/admin`, or **Developer settings → GitHub Apps → <app> → Permissions & events**).
2. Under **Subscribe to events**, select **Pull request review thread**.
3. Save the changes.

The event needs no new permission (it comes with Pull requests), so installations don't have to accept anything. `/admin` uses the same check for the Email addresses permission.

### Adding permissions to an existing app

Apps created before the guide check was added lack Checks and Commit statuses. `/admin` lists the missing ones with a link to the app's permission settings, and **Settings → Automation** points out a missing Checks permission for workspaces with an app installation. To add them:

1. On GitHub, open the app's settings, then **Permissions & events → Repository permissions**. Set **Checks** and **Commit statuses** to **Read and write** and save. No new events are needed.
2. GitHub asks every installation to accept the new permissions: the owner of each account or organization gets an email, and the installation's settings page (**Settings → GitHub Apps → Configure** on GitHub) shows a request to review. Until it is accepted, GitHub answers with 403 and **Settings → Automation** shows the error under **Recent guide checks**.

Nothing has to change in Omakaze; the next update of each pull request's check uses the new permissions.

If `APP_URL` is not reachable from the internet (for example `http://localhost:3000`), GitHub cannot deliver webhooks to it, and the manifest creates the app without a webhook or events. To get webhooks later, give the instance a public URL, remove the stored app on `/admin` and create it again. Sign-in and API access do not depend on webhooks; pull requests are then refreshed by polling and when members open the app.

## Create the app manually

Create a GitHub App in your account or organization settings (**Developer settings → GitHub Apps → New GitHub App**) with the same settings:

| Setting | Value |
| --- | --- |
| Homepage URL | `<APP_URL>` |
| Callback URL | `<APP_URL>/api/auth/github/callback` |
| Request user authorization (OAuth) during installation | Off |
| Setup URL | `<APP_URL>/api/github/setup`, with **Redirect on update** turned on |
| Webhook | Active; URL `<APP_URL>/api/github/webhook`; a random secret |
| Repository permissions | Contents: Read-only; Metadata: Read-only; Pull requests: Read and write; Issues: Read and write; Checks: Read and write; Commit statuses: Read and write |
| Account permissions | Email addresses: Read-only |
| Subscribe to events | Pull request, Pull request review, Pull request review comment, Pull request review thread |
| Where can this GitHub App be installed | Only on this account, or Any account if you want to install it on other accounts |

Expiring user tokens can stay on; Omakaze refreshes them. After creating the app, generate a private key and a client secret, and set:

| Variable | Value |
| --- | --- |
| `GITHUB_APP_ID` | The App ID |
| `GITHUB_APP_SLUG` | The slug from the app's public URL (`https://github.com/apps/<slug>`). Required for the **Install on GitHub** link. |
| `GITHUB_APP_PRIVATE_KEY` | The contents of the `.pem` file. Newlines may be written as `\n`; a base64-encoded PEM is also accepted. |
| `GITHUB_APP_WEBHOOK_SECRET` | The webhook secret. Without it, webhook deliveries from the app fail signature verification. |
| `GITHUB_CLIENT_ID` | The app's Client ID |
| `GITHUB_CLIENT_SECRET` | The client secret |

When `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` are both set, they take precedence over an app created from `/admin`. Restart the server after changing them.

## Install the app on an account or organization

A workspace admin connects an installation from **Settings → GitHub → Install on GitHub**:

1. Link your GitHub account first: sign in with GitHub, or link it on the **Account** page with **Link GitHub account** or a personal access token.
2. Choose **Install on GitHub**. Omakaze sends you to the app's installation page with a signed `state` that names the workspace and your user; it is valid for an hour.
3. On GitHub, choose the account or organization and the repositories, then install.
4. GitHub redirects to the setup URL. Omakaze checks the installation (below), creates or updates the connection, and returns you to **Settings → GitHub**. A new connection is also attached to the workspace's repositories that have [no connection](#repositories-without-a-connection) and that it can access.
5. Add repositories on the **Repositories** page. The list shows the repositories selected for the installation.

### Installation ownership check

The setup URL only links an installation when all of these hold:

- the `state` parameter is valid and was issued to the signed-in user for the workspace;
- the user is still an admin or owner of that workspace;
- the user has a linked GitHub credential (otherwise: "Sign in with GitHub to finish connecting the app.");
- that credential can manage the installation: the installation appears in `GET /user/installations`, or the installation belongs to the user's own GitHub account, or the user is an owner of the organization it belongs to (an active membership with the `admin` role in `GET /user/memberships/orgs/<org>`).

These checks stop someone from linking another account's installation by guessing an `installation_id`. `GET /user/installations` only works with user tokens of the GitHub App itself; credentials linked with a personal access token or through an OAuth App rely on the account and organization checks. If all checks fail, **Settings → GitHub** shows the error `Your GitHub account can't manage the installation on <account>.` Installations started directly on GitHub, without the **Install on GitHub** button, arrive without a `state` and are not connected.

### Private apps and organizations

The manifest creates a private app, and GitHub only allows a private app to be installed on the account that owns it. To use the app with an organization, create it for that organization on `/admin`, or make the app public in its settings on GitHub.

### Uninstalling and suspending

GitHub sends `installation` webhooks to the app:

- `deleted` removes every connection that uses the installation. Their repositories and guides stay in the workspace [without a connection](#repositories-without-a-connection).
- `suspend` marks the connections as suspended; API calls through them fail until `unsuspend`.

## Other ways to connect GitHub

### Personal access token

**Settings → GitHub → Connect with a token** stores a personal access token (encrypted) for a user or bot account. The repository picker lists repositories that the token's user can access (`/user/repos`, up to 300). If the token cannot list repositories, enter `owner/name` instead. See [Token permissions](#token-permissions).

### Linked GitHub account

**Settings → GitHub → Use your GitHub account** creates a connection that uses the GitHub credential linked to your user (through GitHub sign-in or a token on the **Account** page). If the credential is a GitHub App user token, GitHub limits it to repositories where the app is installed. If that credential stops working, for example because a refresh token expired, the connection fails until you sign in with GitHub again. The connection belongs to your user: if you delete your account, the connection is deleted, and its repositories stay in the workspace [without a connection](#repositories-without-a-connection).

### Repository webhooks

For token and account connections, the **Repositories** page has **Create webhook** for each repository. It creates a repository webhook for `pull_request`, `pull_request_review`, `pull_request_review_comment` and `pull_request_review_thread` events (webhooks created before `pull_request_review_thread` or `pull_request_review` was added don't send them; add them in the repository's webhook settings, or delete the webhook and create it again), sent to `<APP_URL>/api/github/webhook` and signed with `GITHUB_WEBHOOK_SECRET` (by default a value derived from `APP_SECRET`). The connection's credential must be allowed to create webhooks on the repository; see [Token permissions](#token-permissions). A GitHub App user token cannot, because the app does not request a webhook permission.

### Polling

Without webhooks, the pull request list is refreshed when members open the workspace or select **Sync**, and the worker polls repositories that have automatic guides turned on every `POLL_INTERVAL_SECONDS`. See [self-hosting.md](self-hosting.md#webhooks-and-polling).

### Removing a connection

**Remove** on **Settings → GitHub** deletes the connection. Its repositories and their guides stay in the workspace without a connection. Nothing is changed on GitHub.

### Repositories without a connection

A repository loses its connection when the connection is removed, when the GitHub App is uninstalled, or when the user behind a linked-account connection deletes their account. The **Repositories** page then shows "No GitHub connection" for it.

- Guides, sections and the cached pull requests are kept. Sections stay readable, and the diff is shown from the stored snapshot, without expandable context.
- Comments are not loaded, and everything else that needs GitHub fails until the repository is reconnected: posting comments and reviews, syncing, polling and AI generation. API and MCP calls get the error `<owner>/<name> has no GitHub connection` (HTTP 409 in the REST API).

A repository is reconnected when:

- an admin adds a connection that can access it: a linked account, a token or a new GitHub App installation (for account and token connections, the confirmation says how many repositories were reconnected);
- an admin adds it again on the **Repositories** page;
- an admin's MCP or REST API call names a pull request of the repository and one of the workspace's connections can access it.

## Webhooks

`POST /api/github/webhook` accepts deliveries from the GitHub App and from repository webhooks.

- The `X-Hub-Signature-256` header must match an HMAC-SHA256 of the body with either the app's webhook secret or the repository webhook secret; otherwise the response is `401`.
- Deliveries are de-duplicated by `X-GitHub-Delivery` and recorded; `/admin` shows the last 15.
- `pull_request` updates the cached pull request. The actions `opened`, `reopened`, `synchronize` and `ready_for_review` also check whether a guide should be generated automatically (see [ai.md](ai.md#automation)). `review_requested`, `review_request_removed`, `assigned` and `unassigned` update the cached requested reviewers, requested teams and assignees that the **Needs my review**, **Mine** and **Assigned** filters use. These actions are part of the `pull_request` event, so existing app installations and repository webhooks receive them without changes.
- `pull_request_review`, `pull_request_review_comment` and `pull_request_review_thread` (a conversation resolved or unresolved) update the cached pull request and drop its cached review comments and review threads, so the next request reads them from GitHub.
- A reply in a review conversation (`pull_request_review_comment` with the action `created`) emails the members who wrote in the conversation, and a submitted review (`pull_request_review` with the action `submitted`) is posted to the workspace's Slack or JSON webhook when it has one. A comment or review posted through Omakaze and its webhook count as one event. See [configuration.md](configuration.md#notifications).
- `installation` handles `deleted`, `suspend` and `unsuspend` as described above.
- Other events and actions are recorded as ignored.

## Sign in with GitHub

**Continue with GitHub** appears on the sign-in page when an OAuth client is available:

- **GitHub App (recommended).** An app created on `/admin` provides its client ID and secret automatically. For an app configured with environment variables, set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` to the app's own client credentials. No OAuth scopes are requested; access follows the app's permissions and the user's own access. GitHub App user tokens can expire; Omakaze stores the refresh token encrypted and refreshes the access token when it is within two minutes of expiry.
- **OAuth App.** Leave `GITHUB_APP_ID` empty and set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` from an OAuth App whose callback URL is `<APP_URL>/api/auth/github/callback`. Omakaze requests the scopes `read:user user:email repo`. With a GitHub App installed as well, the [installation ownership check](#installation-ownership-check) relies on the account and organization checks for these users.

When `GITHUB_APP_ID` is set, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are treated as the GitHub App's credentials.

Sign-in behavior:

- An existing user is matched by GitHub user ID. Accounts are never merged by email.
- New users are created only when sign-up is allowed: `AUTH_SIGNUP_ENABLED=true`, a valid invite link, or an instance with no users yet.
- Omakaze reads the user's verified GitHub email addresses (`/user/emails`, plus the public profile email). A new user gets one of them, preferring one in `AUTH_ALLOWED_EMAIL_DOMAINS`, and it counts as confirmed. If that address already belongs to another user, the new user is created without an email.
- When `AUTH_ALLOWED_EMAIL_DOMAINS` is set, a new user without an invite link needs a verified GitHub email in one of the domains.
- When an existing user signs in with GitHub or links GitHub, their email counts as confirmed if it is one of their verified GitHub addresses. Confirmed addresses are needed for [email-restricted invites](configuration.md#invites).
- Signed-in users can link GitHub later on the **Account** page, with **Link GitHub account** or with a personal access token.
- With `AUTH_GITHUB_TOKEN_ENABLED=true`, the sign-in page also accepts a personal access token. The token becomes the user's linked GitHub credential, and the same email rules apply.

The linked credential is used to post comments and reviews as the user, for **Use your GitHub account** connections, and for the installation ownership check.

## Posting comments and reviews

- Line comments, replies and reviews are posted with the reviewer's linked GitHub credential. Without one, or if GitHub rejects it with 401, 403 or 404, they are posted through the workspace connection with the footer `Posted by <name> via Omakaze`.
- **Approve**, **Request changes** and resolving conversations require a linked GitHub account; they are never done through a connection.
- Without a linked account, **Comment** in the review panel posts a comment in the pull request conversation through the connection.
- You can delete line comments and replies that you posted through Omakaze, and line comments on GitHub written by your linked account.
- **Insert suggestion** in a line or multi-line comment (or a reply) adds a ```` ```suggestion ```` block with the commented lines of the head side, as GitHub does. The suggestion is posted as an ordinary comment body. Suggestions in comments are shown as a small diff of the commented lines (taken from the `diff_hunk` GitHub returns with each comment) and the suggested ones. They are committed on GitHub (**Commit on GitHub** opens the comment); Omakaze doesn't commit them, so it needs no Contents write permission.
- **Resolve conversation** and **Unresolve conversation** use GitHub's GraphQL API: `pullRequest.reviewThreads` maps review comment IDs to thread IDs, and the `resolveReviewThread` and `unresolveReviewThread` mutations change them. The GraphQL endpoint is derived from `GITHUB_API_URL` (`https://api.github.com/graphql`, or `https://<host>/api/graphql` on GitHub Enterprise Server). Like **Approve** and **Request changes**, resolving needs a linked GitHub account and is never done through a connection: branch protection can require resolved conversations before merging, so GitHub's rules on who may resolve (the pull request author and people with write access to the repository) apply to you, and GitHub shows you as the one who resolved it. The activity log records it too.
- If the GraphQL API can't be read (for example a token without access to it), comments still load, without the resolve buttons.
- Agents over MCP post replies, line comments, conversation comments and reviews, and resolve conversations, with the same rules, as the member whose token they use. They can approve only when a workspace admin allows it (see [mcp.md](mcp.md#reviewing-over-mcp)).
- Summary comments (see [ai.md](ai.md#automation)) and the [guide check](#guide-check) are posted through the connection.

## Guide check

When the guide check is on (**Settings → Automation**, see [configuration.md](configuration.md#guide-check)), Omakaze reports review progress on the head commit of every open pull request, with a link to the pull request in Omakaze. How it is posted depends on the repository's connection:

| Connection | Posted as | Name on GitHub |
| --- | --- | --- |
| GitHub App installation | A check run (Checks API), created on the head commit and then updated in place | `Omakaze guide` |
| Personal access token, linked GitHub account | A commit status (`POST /repos/<owner>/<repo>/statuses/<sha>`); GitHub only lets apps create check runs | `omakaze/guide` |

| Situation | Informational | Require review: check run | Require review: commit status |
| --- | --- | --- | --- |
| Every section reviewed by enough members | neutral (status: success) | success | success |
| Some sections not reviewed yet | neutral (status: success) | action required | pending |
| The latest guide covers an older commit | neutral (status: success) | action required | pending |
| No guide yet | neutral (status: success) | action required | pending |
| A guide is being written for the head commit | in progress (status: pending) | in progress | pending |

The check run's title is the progress, such as "3 of 6 sections reviewed", and its summary lists every section with who reviewed it. A commit status carries the title as its description. The check is updated when a guide is started, published, failed or deleted, when review marks change, when a pull request is opened or gets new commits (webhook, polling or sync), and when the setting changes. Updates are queued as `update_guide_check` jobs that wait 5 seconds, so a burst of review marks produces one update. Closed pull requests are not updated. When the check is turned off, pull requests that had one get a last update ("Guide check turned off", neutral, or a successful status) so it no longer blocks merging.

To block merging until the guide is reviewed, choose **Require review** and add `Omakaze guide` (app installations) or `omakaze/guide` (other connections) as a required status check in the branch protection rules or a ruleset of the repository. GitHub only offers a check there after it has been reported once in the last week.

If GitHub refuses an update, for example because an older app lacks the Checks permission (see [Adding permissions to an existing app](#adding-permissions-to-an-existing-app)) or a token cannot create commit statuses, the error is shown under **Recent guide checks** in **Settings → Automation** and in the pull request header.

## Token permissions

Personal access tokens are used for token connections, token sign-in and linking an account with a token.

| Token type | Required | For the guide check | For **Create webhook** on the Repositories page | To read verified email addresses |
| --- | --- | --- | --- | --- |
| Fine-grained | Access to the repositories; Contents: Read-only; Metadata: Read-only; Pull requests: Read and write | Commit statuses: Read and write | Webhooks: Read and write | Account permission Email addresses: Read-only |
| Classic | `repo` | Included in `repo` | `admin:repo_hook` | `user:email` |

Creating repository webhooks also requires the token's user to be an admin of the repository. Without permission to read email addresses, token sign-in and linking use only the public email of the GitHub profile.
